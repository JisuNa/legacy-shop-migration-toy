# 사용한 프롬프트

| 항목 | 내용 |
|---|---|
| 도구 | Claude Code, `grill-me` 스킬(설계 인터뷰) |
| 모델 | 설계 인터뷰: Claude Fable 5.1 / 구현·문서·리뷰 서브에이전트: Claude Opus 5.5 |
| 기간 | 2026-11-07 ~ 2026-11-08 |
| 진행 방식 | AI가 설계 질문마다 선택지와 추천안을 제시하고, 지원자가 선택하거나 수정 지시를 내렸다. 열린 질문이 없어진 뒤 구현을 시작했다 |

이 문서의 구성은 다음과 같다.

1. **시작 프롬프트**: 원문 그대로다.
2. **설계 인터뷰**: 질문별로 AI가 제시한 선택지, AI 추천, 지원자의 결정을 정리했다. 지원자 답변은 결정 내용을 문장으로 옮겼고, 과제 결과물에 영향을 준 질문만 남겼다. 질문 번호(Q)는 인터뷰 당시 번호이며 `AI_REFLECTION.md`가 같은 번호를 참조한다.
3. **구현·검토 단계 지시**: 설계 합의 이후 내린 작업 지시를 정리했다.
4. **사용한 서브에이전트**: 위임한 작업과 결과다.

---

## 1. 시작 프롬프트 (원문)

```
너는 20년의 경력이 있는 백엔드 개발자이면서 장바구니, 상품, 재고, 가격, 주문, 결제, 포인트 커머스 흐름 전문가야. 레거시 시스템을 신규 시스템으로 전환할거야. legacy_db.sql 테이블 구조를 파악하고 현재 구조에서 문제가 되어 해결이 필요한 지점들이 있는지 검토해줘. 온라인의 신뢰있는 자료를 기반으로 근거 있는 결과물 만들어줘. 공식 레퍼런스, 모범 사례(best practice), 표준 명세, 회사 공식 테크/기술 블로그(카카오, 카카오페이, 카카오뱅크, 라인, 당근, 컬리, 우아한형제들, 무신사, AWS, 우버, 넷플릭스, 클라우드플레어, stripe) 등
```

첨부: 과제 안내문 이미지 3장(배경, 요구사항, 제출물, 기술 제약, 실격 요건), `legacy_db.sql`

AI는 이 프롬프트로 레거시 스키마의 결함 10개(F1~F10)를 시드 데이터 행 단위 증거와 함께 정리했고, 이를 바탕으로 아래 인터뷰를 진행했다.

## 2. 설계 인터뷰

### 2.1 문제 정의와 접근 방식

**Q1. 결함 분류 기준**
- 선택지: 결함 10개를 "금액 정합성 > 동시성 > 모델링 > 위생" 순서로 묶어 DESIGN.md 문제 정의에 쓸지
- AI 추천: 위험 유형으로 묶고, 각 결함에 시드 데이터 증거 행을 붙인다
- 결정: 추천안 채택. 문서는 장황하지 않게 핵심만 쓴다

**Q2. 코드로 증명할 "가장 위험한 지점"**
- 선택지:
  - (a) 복합결제 원장과 부분취소 배분
  - (b) 주문·결제 상태 정합성과 멱등성
  - (c) 세일 오픈 시 재고 동시성
- AI 추천: (a). 시드 데이터의 결함이 가장 많이 몰려 있고, 과제 배경이 복합결제를 명시한다. (c)는 SQLite가 쓰기를 하나씩만 처리해 동시성 증명이 약하고, (b)는 외부 PG 없이 테스트하면 모킹 비중이 크다
- 결정: (a)

**Q4. 스키마만으로 알 수 없는 레거시 동작의 처리**
- AI 추천: "세운 가정"에 번호를 붙여 적고, 가정이 틀리면 무엇이 바뀌는지 함께 쓴다
- 결정: 추천안 채택. DESIGN.md 5절 "세운 가정" A1~A10

### 2.2 결제 원장 설계 (요구사항 3)

**Q7·Q16. 결제 테이블 구조와 이름**
- AI 제안: 결제를 3층(주문 단위 → 수단 단위 → 승인·취소 1건 단위)으로 나누고 `payment` / `payment_line` / `payment_entry`로 이름 짓는다. 쿠폰은 결제수단이 아니라 주문 할인으로 둔다
- 결정: 3층 구조와 쿠폰 처리는 채택. 이름은 역할이 바로 전달되지 않아 **`payment_master` / `payment_detail` / `payment_transaction`**으로 정했다

**Q8. 부분취소 금액을 결제수단별로 나누는 규칙**
- 선택지: 수단별 결제 비율로 비례 배분 / 포인트를 먼저 전액 환불
- AI 추천: 비례 배분. 1원 단위 잔차는 최대잔여법으로 처리해 합계를 항상 맞춘다
- 결정: 비례 배분

**Q9. 멱등키 범위**
- AI 제안: 승인·취소 요청마다 멱등키를 받아 DB UNIQUE로 강제하고, 같은 키 재요청은 저장된 결과를 돌려준다. PG 타임아웃 후 재시도를 테스트로 증명한다
- 결정: 채택

**Q10·Q17. 취소 시 쿠폰·포인트 복원 정책**
- AI 제안: 전체취소는 쿠폰 복원, 부분취소는 할인액을 품목 비례로 차감하고 포인트만 복원한다
- 지원자 질문: 쿠폰에 최소 결제금액 조건이 있으면 부분취소 후 조건을 어기는데 고려했는가
- AI 답변: 레거시 스키마에 최소 결제금액 컬럼이 없어 고려하지 않았다. 추가한다면 부분취소를 막고 전체취소만 허용하는 방안이 있다
- 결정: **레거시에 없는 정책은 추가하지 않는다.** 가정 A2로 남긴다

**Q53·Q56. 원장에 상태를 둘지**
- 경위: 지원자가 "모든 신규 테이블에 생성·수정 시각을 둔다"고 지시했고, AI가 원장 테이블에도 수정 시각을 두려 했다
- 지원자 지적: 원장은 추가만 하는 기록이므로 상태가 바뀌면 안 된다
- AI 수정안: 원장에는 생성 시각만 둔다. PG 타임아웃처럼 결과를 모르는 상태는 별도의 요청 테이블(`payment_request`)에서 관리하고, 결과가 확정된 거래만 원장에 기록한다
- 결정: 수정안 채택

**Q57. 결제 금액 검증**
- 선택지: 요청 본문의 금액을 신뢰 / 결제 서비스가 주문 서비스에 금액을 조회해 대조
- AI 추천: 조회 후 대조
- 결정: 조회 후 대조. 테스트에서는 WireMock이 주문 서비스 역할을 한다

### 2.3 전체 구조 (요구사항 1)

**Q19·Q23·Q26. 서비스 경계**
- 선택지: 배포 단위 1개 안에 도메인별 모듈 / 상품+재고·주문·결제를 서비스 3개로 분리
- AI 추천: 배포 단위 1개. 서비스 간 정합성을 단일 트랜잭션으로 지킬 수 있다
- 결정: **서비스 3개로 분리하고 서비스마다 DB를 둔다.** 서비스 간 변경은 이벤트로 전달한다(DESIGN.md 2.1)

**Q12·Q33. 서비스 간 이벤트 전달**
- 지원자 질문: Kafka를 띄울 수 없는데 outbox 패턴을 전제로 코드를 쓸 수 있는가
- AI 답변: 각 서비스 DB에 outbox 테이블을 두고 같은 트랜잭션으로 이벤트를 기록한다. 운영에서는 Debezium이 Kafka로 내보내고, 수신 측은 이벤트 ID로 중복을 버린다
- 결정: 채택. 결제 서비스 코드는 outbox 행 기록까지 구현한다

**Q32·Q43. 재고 선점 방식**
- 지원자 요청: 재고 선점을 outbox 이벤트로 설계하는 사례를 기술 블로그에서 찾아 근거를 달라
- AI 조사 결과: 이벤트로 선점하는 국내 운영 사례는 찾지 못했다. 우아한형제들 선물하기는 선점을 동기 호출로, 해제만 이벤트로 처리한다. 이벤트 방식은 고객이 품절 여부를 늦게 알고 세일 오픈 때 보상 이벤트가 몰린다
- 선택지: 동기 선점 + 이벤트 해제 / 전부 이벤트(saga)
- 결정: **동기 선점 + 이벤트 해제**

**Q29·Q47. 재고 차감 시점**
- 선택지: 주문 생성 시 선점 / 결제 완료 시 차감
- AI 추천: 주문 생성 시 선점, 결제 완료 시 확정, 취소·결제 실패·가상계좌 만료 시 해제
- 결정: 선점 채택. 고객용 선점 API를 따로 두지 않고 주문 생성 처리 안에서 선점한다

**Q30. 가격 변경 처리**
- AI 제안: 장바구니는 현재가를 보여 주고, 주문 생성 시점 단가를 주문 품목에 고정한다. 장바구니 가격과 다르면 주문을 막지 않고 변경 사실을 응답에 담는다
- 결정: 채택

**Q22. 동시성 방어 지점**
- 지원자 요청: MySQL을 쓴다면 시점별로 어떤 잠금이 적절한지 정리해 달라
- AI 답변: 한 문장으로 끝나는 조건부 UPDATE를 우선하고, 조회 후 판단이 필요할 때만 `SELECT ... FOR UPDATE`를 쓴다
- 결정: 조건부 UPDATE와 UNIQUE로 막는다. SQLite와 MySQL에서 같은 SQL로 동작한다(DESIGN.md 2.4)

**Q24·Q27. 식별자**
- 지원자 질문: 주문번호에 자동증가 정수를 쓰지 않는 이유는 무엇인가
- AI 답변: 내부 키는 자동증가 정수를 쓴다. 외부에 노출하는 주문번호는 주문량 노출, 번호 추측 조회, 공존 기간 채번 충돌 때문에 시간 + 난수 문자열로 둔다
- 결정: 두 키를 함께 쓴다

### 2.4 레거시 DB와 신규 DB의 분리, 공존 (요구사항 2)

**Q36. 공존 기간 주문 데이터의 원천**
- 선택지: 주문 단위 라우팅(신규 주문은 신규 DB가 원천) / 레거시를 원천으로 두고 신규를 섀도우로 운영한 뒤 교체
- AI 추천: 주문 단위 라우팅. 주문 생성 지점 한 곳에서 신규 비율을 정하고, 비율 0으로 되돌린다
- 결정: 주문 단위 라우팅

**Q42. 레거시 테이블에 쓰는 값**
- AI 제안: 신규 주문을 레거시 테이블에 기록할 때 레거시 코드값만 쓴다. 새 코드값을 넣으면 레거시 화면을 고쳐야 해서 무중단이 깨진다
- 결정: 채택

**Q60. 공유 자원(포인트 잔액·재고·쿠폰)의 원천** (리뷰 후 추가)
- 경위: 독립 리뷰에서 "주문 단위 라우팅은 공유 자원을 나누지 못해 이중 사용과 오버셀이 가능하다"는 지적이 나왔다
- 선택지:
  - (a) 전환 완료 전까지 레거시 테이블을 원천으로 두고, 신규 서비스가 조건부 UPDATE로 직접 차감
  - (b) 전환 첫날 신규로 이관하고 레거시 코드가 신규 API를 호출
- AI 추천: (a). 문서와 개발자가 없는 레거시 코드를 고치지 않아도 된다
- 결정: (a)

### 2.5 제출 범위와 기술 스택

**Q13·Q44·Q45·Q50·Q51. 요구사항 2를 코드로 구현할지**
- AI 제안: 레거시 DB 파일을 띄우고, 레거시 동기화 전담 서비스와 레거시 결제 이관 코드를 함께 구현한다
- 결정: **요구사항 3만 코드로 작성하라는 과제 문구에 따라, 요구사항 2는 설계 문서로만 다룬다.** 레거시 DB 파일, 동기화 서비스, 이관 코드는 만들지 않는다

**Q35·Q40·Q52·Q55. 코드와 테스트 범위**
- AI 제안: 서비스 3개를 함께 띄우는 통합 테스트 모듈과 실행 스크립트를 둔다
- 결정: **요구사항 3에 해당하는 결제 서비스 하나와 그 테스트만 작성한다**

**Q18·Q20·Q59. 기술 스택**
- 지원자 요청: Spring Boot 기반 의존성 목록에서 꼭 필요하지 않은 것을 빼 달라
- AI 정리: H2·MySQL 드라이버 대신 SQLite 드라이버와 SQLite 방언을 쓴다. Flyway는 SQLite를 공식 지원한다
- 결정: Spring Boot 4, Kotlin, SQLite + Flyway + JPA, Kotest, WireMock

**Q25·Q28. ADR 주제**
- AI 제안: 결제 원장 / 레거시·신규 공존 / 모듈 분할
- 지원자 판단: 모듈 분할은 과제의 핵심 설계 결정이 아니다
- 결정: **결제 원장과 부분취소 / 레거시·신규 DB 공존 / 재고 선점** 3건
